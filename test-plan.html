D3 / Test Plan

Test Plan

Status: Executable team plan, updated October 26, 2026. Client CAD versions, permitted production samples, and acceptance dates still require confirmation.

Purpose and quality risks

This plan gives Team E, the client, and another engineer enough information to repeat the tests. The highest risks are incorrect physical scale, open or duplicate cut paths, loss of holes, excessive segments, unsupported CAD entities, color-region errors, and output that opens successfully but is unsuitable for fabrication.

Part 1: testing with full time and access

  • Build a client-approved corpus covering clean logos, low-resolution art, transparency, gradients, photographs, many colors, holes, adjacent regions, text, and PDF pages.
  • Compare every output with accepted CAD reference files using geometric distance, area, path closure, topology, scale, layer, and native-entity checks.
  • Run automated unit, integration, property, fuzz, performance, and regression tests on every supported operating system and Python version.
  • Test installation, first use, error recovery, and export with representative Adcut operators.
  • Import outputs into every supported AutoCAD and IGEMS version, then complete supervised water-jet trials with approved material and safety procedures.
  • Retain expected outputs and signed acceptance results for future regression testing.

Part 2: committed semester testing

Team E will maintain automated tests for deterministic logic and will record manual evidence for the browser workflow and downstream CAD checks. Claims in the final report will distinguish tests that passed from tests that remain blocked.

Environments

  • GitHub Actions: Windows, Ubuntu Linux, and macOS with Python 3.11, 3.12, and 3.13 using the committed uv.lock.
  • Primary local check: Windows 11, Python 3.12, Streamlit 1.50 or the locked project version, Chrome and Edge. Exact browser versions will be recorded with results.
  • Client environment: Windows workstation. AutoCAD and IGEMS versions remain unconfirmed and must be recorded before acceptance testing.
  • Final package: the locked uv workflow is testable now; a standalone Windows package will receive a clean-machine test after packaging is selected.

Entry, exit, and reporting

A test starts only with versioned code, identified input, recorded settings, and an expected result. A feature exits testing when required automated checks pass, manual evidence is stored, and no unresolved high-severity defect contradicts D1. Failures become GitHub issues with reproduction steps. Client-dependent tests remain “blocked,” never “passed,” until evidence exists.
