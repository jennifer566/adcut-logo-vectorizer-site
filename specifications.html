Purpose and intended users

The project brief describes a local Windows tool for Adcut that converts customer logos into 2D CAD drawings for water jet cutting. Different logo colors represent different flooring or turf materials, so color boundaries must become separate closed vector paths. Intended users identified in the brief are Adcut operators and CNC programmers.

Initial functional requirements

The following are drawn from the project brief and remain subject to client validation:

  • Accept JPEG, PNG, WEBP, GIF, and PDF input.
  • Provide configurable color reduction to separate material regions.
  • Trace color boundaries into closed vector paths without gaps or overlaps.
  • Allow review and adjustment before export.
  • Export SVG and R12/R2000 DXF files.

Proposed workflow: upload image → color reduction → vectorization → review and tweak → SVG/DXF export.

Initial non-functional requirements

  • Run locally on Windows.
  • Use an open-source, commercially viable stack.
  • Provide an intuitive interface for operators.

Supported Windows versions, hardware requirements, processing-time targets, accuracy tolerances, and measurable usability criteria have not been confirmed.

Draft user stories

These are team interpretations of the project brief, not statements collected from a client interview.

  • As an Adcut operator, I want to import customer artwork so that I can prepare it for CAD conversion.
  • As an Adcut operator, I want to reduce colors into material regions so that each region can be represented by closed paths.
  • As an Adcut operator, I want to review and adjust the traced result before exporting it.
  • As a CNC programmer, I want SVG or DXF output that can be used in the downstream cutting workflow.

Story priorities and acceptance criteria are pending client input.

Interfaces and implementation options

The brief proposes Streamlit or React/Vue for the interface, OpenCV for image processing, Potrace/vtracer for tracing, ezdxf for CAD export, and Docker/PyInstaller for development or packaging. These are candidate technologies, not final design decisions.

The downstream CAD/CAM software, required DXF entities, units and scale, layer conventions, and installation approach are not yet confirmed. No screen layout or detailed interface behavior has been approved.

Questions sent to the client

Jennifer Lee sent the following questions to Nick Dokich on behalf of COMP 523 Team E after the planned meetings could not take place. The exact send date is not recorded here. All answers remain pending as of September 20, 2026. Examples in the questions are possibilities for discussion, not agreed requirements.

  1. Users and workflow

    Who do you expect to be the primary user of the tool?

    What would their typical workflow look like from receiving a logo to exporting the final file?

  2. Core functionality and priorities

    What functionality would you consider absolutely necessary for the final product?

    Which features would you consider must-haves versus nice-to-haves?

  3. Input files

    What types of input files do you most commonly receive from users?

  4. Color and vectorization behavior

    What should the program produce from each color in a logo?

    For example, should every distinct color or material become its own separate closed vector path or layer?

  5. Editing capabilities

    What editing capabilities would you like after the initial vectorization?

    For example, should users be able to merge colors, delete regions, adjust paths, change detected colors, or manually correct boundaries?

  6. SVG and DXF export requirements

    Are there specific requirements for the exported SVG or DXF files?

    For example, are there requirements for DXF version, units, scale, layers, closed paths, naming conventions, or compatibility with software or machines you currently use?

  7. Performance and usability

    Are there any performance or usability expectations we should design around?

    For example, how quickly should a typical logo be processed, and how much technical knowledge should we assume the user has?

  8. Technical constraints

    Are there any additional constraints we should be aware of?

    We currently understand that the application should run locally on Windows and use an open-source stack. Should it also work completely offline? Are there any other restrictions related to installation, customer files, or external services?

  9. Difficult or invalid inputs

    How would you like the program to handle difficult or invalid inputs?

    For example, very low-resolution images, gradients, photographs, logos with many colors, open contours, or files that cannot be converted cleanly.

  10. Success criteria

    At the end of the semester, what would make you consider the tool successful?

No numerical thresholds, performance promises, or final scope commitments are set in this draft.
